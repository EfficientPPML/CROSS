# Synchronous-execution successor scope

The frozen194-test/35-source ideal predecessor remains unchanged. Its structural and retained-array guards were successful ideal checks, but it accepted ordinary arithmetic with `low_memory=False`. Production `EncryptedPolynomialEvaluator._finish` calls `jax.block_until_ready` only when low-memory mode is enabled. Thus its callback-lifetime tests did not establish a general asynchronous execution contract.

This new isolated successor requires exact `True` for arithmetic.low_memory, refresher.evaluator.low_memory and refresher.engine._low_mem. It also requires the original ordinary facade `_finish` function bound to the actual arithmetic/evaluator object, records that accessor at construction, and rechecks all flags and accessors before work and after callbacks. No numeric operation, mask, coefficient, domain, iteration, event, profile or scale equation changes. The PV bypass successor has the same arithmetic restriction.

The actual frozen BERT stage4 execution source constructs its arithmetic, linear facade and refresher with low_memory=True; it also blocks the final output. The copied reference is `execution_references/full_model_engine.py`, taken from its actual-v2 execution tree. Its key loader quarantines public mappings and reachable transfer owners on an entered-server-body failure and requires dedicated-process exit. The Qwen full-model/file-stage engine has not been implemented, so that integration is not implied by these Qwen owners.

Focused tests execute the unchanged production `_finish` AST with an explicit mock barrier, showing that the barrier precedes a callback on success and that barrier exceptions/cancellation prevent callback entry and preserve the primary exception. The test JAX module is a temporary mock; no actual backend or HE runs. Separate tests reject false, missing and equality-alias flags, foreign/custom `_finish` owners/functions, and first/final callback replacements in both owners. NumPy ideal arithmetic is synchronous already; its declared flag is an explicit test seam, not an async simulation.

This is a successful-barrier/callback contract. If a real barrier raises, readiness is unknown. This owner neither closes its borrowed context nor certifies reclamation of pending arrays. A future Qwen engine must enforce the same dedicated-process failure/quarantine policy as the reviewed key loader, retain all required resources and exit rather than reuse the failed process. It must not infer successful cleanup from these public tests. External callback side effects and process-wide signal atomicity are likewise outside the claim.
