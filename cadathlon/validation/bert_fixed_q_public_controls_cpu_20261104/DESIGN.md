# Fixed-Q registration versus physical control diagnosis

This follow-up keeps every active d8 profile and every validator unchanged. It asks why three physically covered, table-secure public profiles fail strict registered validation. No CKKS context, keys, plaintext/ciphertext objects, encryption, decryption or HE execution is permitted.

The frozen validator explicitly estimates OpenFHE HYBRID digits from50 logical composite moduli and requires exact P count, exact reference-generated Q/P, and equality between the logical estimate and the physical bit-count estimate. The actual key generator and full-key rotation controls partition100 physical Q limbs with alpha=ceil(100/dnum); lower levels keep this max-Q alpha. For d8 this is13 limbs versus a logical bound of7 composites/14 limbs; for d6 it is17 versus9 composites/18 limbs. These are different policies.

There is another independent distinction: compute_num_p_towers is a bit-count lower bound, while generate_p_towers extends the actual prime list until its product covers the largest exact physical partition after excluding Q primes. Frozen outcomes are logical/physical-lower-bound/generated counts15/13/14 for d8 aux30,19/17/18 for d6 aux30, and18/17/17 for d6 aux31. Adding P alone cannot satisfy all existing exact-policy checks. These observations do not relabel any registration rejection as acceptance and do not contradict the separately measured custom-profile kernel/security gates.

The next bounded public probe would call the actual imported _HERotKernel constructor and control_gen with the actual frozen primes, batch1, degree layout256x512, perf_test=False and keygen_sizeQ=100 for all50 prefixes of each profile. The real finite-field and BConv control objects/coefficients are allowed. A supplied polynomial_factory returns only immutable shape/modulus descriptors, avoiding every Polynomial/NTT/payload allocation. Empty key placeholders created by the kernel are allowed; setup_rotation, key creation, codec methods, ciphertext operations, real Polynomial/CKKS/parameter-cache construction remain denied. CPU backend initialization must be recorded. Thus this is actual public control construction with descriptor substitutions, not complete kernel/HE acceptance.

Independent checks compare actual selected tower lists to consecutive max-Q partitions, exact P coverage, P inverse residues, BConv source/target inventories and descriptor shapes. Every public control buffer must complete before release. Actual registered validator rejection remains a separate required result. Source hashes and exact inputs are captured before/after/archive; no source/profile mutation is part of the experiment.

A possible future physical-partition profile would need an explicitly named contract distinct from exact OpenFHE registered compatibility, with coherent generation/validation/security rules and new source-bound controls, key generation and numerical proofs. This plan neither implements nor authorizes such a profile. It establishes no precision, latency, peak-memory or full-model result.
