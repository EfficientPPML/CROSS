# Independent production metadata oracle

`production_metadata.ProductionMetadata` executes **21 unchanged production AST method bodies** from the frozen factored-shallow component, including weighted_sum, plaintext multiply, composite rescale, additive facade/kernel checks, level reduction, CompiledArithmetic rotation, and Polynomial cloning/validation. Exact input source bytes and original paths/hashes are recorded in `input_sources/` and `source_inputs.json`.

The oracle substitutes only encoding/payload arithmetic, readiness, and security with inert doubles. Payloads have full-ring **virtual** shape metadata (N131072, CD2, Q100/P14, layout256×512), but their data are small public float64 samples. It never creates a JAX backend/context, performs finite-field arithmetic, reads keys or model tensors, encrypts or decodes. It is a metadata proof, not a cryptographic or full-slot numerical proof.

API: instantiate `ProductionMetadata()`, construct `Value(scale,level, data=..., nsd=1)`, then call `.weighted_sum(values,weights,bias=...)`, `.add(left,right)`, `.raw_add(left,right,level)`, `.rotate(value,index)` or `.rescale_only(value,source,target)`. `metadata(value)` returns the actual AST-produced scale, NSD, Q prefix and shape. The oracle does not import the scale planner; tests independently compare its output against the copied planner.

The tests cover four-baby groups, three/four giant groups and exact metadata additions at L49/L25, canonical and seven noncanonical positive scales, negative/zero weights, zero-index aliasing, ordered-prefix lowering, and actual facade rejection cases. A zero-weight first term still owns weighted_sum metadata. HEAdd accepts scales within its `1e-12` relative tolerance and retains the left scale; it does not force exact equality. Its legacy NSD comparison admits `True == 1`. The new BSGS owner must enforce exact group scales and exact-int NSD1 itself. Finite positive source scales also need representable alignment and sufficient encoded coefficient resolution: extreme positive scales can fail the original finite-alignment/round-away checks.

The first development run had 45 functional passes and one test bookkeeping failure: the extracted-method count was mistakenly asserted as19 instead of21. Its exact sources and log are retained under historical/development-v1 and development-v1.log. No arithmetic implementation changed to correct that assertion.
